| 0015 | summary | A public build log generated from the repository, as a separate project with a default-deny allowlist | The build log is a separate static project that holds no content of its own. A generator reads the decision records, two registries and the commit history, and writes the one file the pages render. One registry lists every component with its stage and is checked against the code. The other is an allowlist: nothing is published without a row, and a blocklist is the second guard. Each decision shows its decider and its proposer, parsed from the record. Rejected: a route inside the product app, which would share a deployment with internal tools; publishing documents verbatim; deriving stages from the code alone, which cannot tell a spike from finished work; a portfolio page written by hand at the end, which asserts involvement instead of showing the record. |
| 0016 | summary | Products are discovered from external sources as candidates, and the catalogue grows only by confirmation | A discovery service searches the catalogue first and external sources second, kept apart and always in that order, so a product already held is never offered as new. The external-data layer gains a second output type for this: a product candidate, which carries a title, a brand, the identifiers a source exposes and where each came from. A candidate is not a fact. Nothing is created from a search alone, and a candidate becomes a product, a variant and its identifiers only when the developer confirms the fields. The first external source is free; a paid aggregator is the next rung, in a later change. Rejected: the paid aggregator first, which spends quota where a free source already answers; automatic creation from a search, because a wrong product family poisons price history; a general framework for every product category now, since matching quality follows identifiers and the single starting category stands. |
| 0017 | summary | A local index of candidate products, seeded cheaply and learned from use, searched as you type | Product search runs on the developer's own database, not on external sources. A local index holds one row per candidate product seen: it is seeded cheaply from one source, grows from every search and every identifier read, and is searched with a trigram index in Postgres as the developer types. The index is never a fact table; it is a snapshot that can be wiped and rebuilt, and nothing in the catalogue references it. Adding a product stays a confirmed action. A paid aggregator is consulted only on an explicit search that the local index cannot answer, under a daily cap. Rejected: calling external sources on every keystroke, which is too slow and too costly; a full pull of a large source whose terms are unread; a separate search engine, a second system for a few thousand rows that the database already handles. |
| 0018 | summary | One public task board is the single list of what to do next | The task list is a public project board linked to the repository, with five columns from Later to Done. Work is grouped into epics, each an issue, and its tasks are sub-issues. Only engine-building tasks go on the board; other items are closed or parked in the status document. A session starts by reading the status document and then the board, and ends by moving the card. A pull request names its issue, so the issue closes when the pull request merges. The developer writes the cards. Rejected: a separate hosted tracker, which would sit outside the repository's record; a heavier suite for a one-person project; an unversioned board held outside the repository; keeping the lists in the status document, which was duplicated elsewhere. |
| 0019 | summary | The free sources answer before the paid one, and the index learns a category, its route and its identifiers | A review of the data model and the build, against the goal of searching products and gathering data cheaply and securely across product types, found six things: the search spent a paid aggregator call where the free sources would have answered; the one product category lived in code rather than data; few index rows carried a barcode, so grouping across stores failed; a placeholder barcode could merge unrelated products; product families split on letter case; and a hosted database API would expose every table once a production project existed. The search now climbs a ladder: the local index, then the free sources, whose answers are remembered, then the index again, and the paid aggregator only when the index is still short, under the same daily cap. A barcode of one repeated digit is rejected in code and by the database. A product family is one row whatever its casing. Each index row now carries the project's own category, mapped from the store's label or the title, the route the offer came by, and when its product details were read, so an identifier read can run in bulk over the store's own product list, bounded per run, each product read once. Two more product lists are seeded, one of them the first outside the starting category, to exercise the category mapping. One general model-code rule now reads hyphenated codes, and the paid price search uses it in place of a one-brand pattern. The database API finding is a procedure in the runbook, to be closed before the first deploy. Rejected: asking the free sources and the paid aggregator together; a category table before the public pages need navigation; a retailer collection table before the retailers service exists; an identifier read for every candidate on every search; wiping the index instead of backfilling the route; per-brand model-code parsers; recording listed prices as price observations before the observations service exists. |
| 0020 | summary | An assistant with web search proposes dated price pages; the page, not the assistant, states the price and the date | The archive captures that draw the history chart are sparse: sixteen points in a year for the one tracked product, and fewer for most. A comparison of five assistant routes against those captures found that an assistant finds real pages well and reads dates off them badly: every date it stated itself was wrong by about two weeks. So the assistant proposes pages and nothing more. Each proposal is a claim. The source fetches the cited page itself, finds the quoted fragment, dates the point from the page or its address, and a pure rule function assigns confidence from what it found. Only a point verified on its page is drawn solid, ranked below an archive capture and below a live page read. A list of permitted sites is held in code with a note on each site's terms; a site whose terms forbid redisplay is never added. Spend is capped three ways: a hard limit on the account, a daily cap counted from the ledger, and a cap on tool calls per request; when the ledger cannot be read, the search is skipped rather than spent blind. Every charted point links to the page it was verified on. Scope now is one product, with nothing persisted. This amends an earlier record's rule that an assistant-read price never reaches a chart, for the one case of a point verified on its page. Rejected: the assistant stating the price and the date, which misdated every point; no site filter, which brought in sources whose terms forbid redisplay and sixteen of eighteen points that could not be checked; a paid history service, on cost and unstated redistribution terms; two other assistant routes, one that rarely searched and one that returned a single list price; the archive alone, which misses the catalogue and deal-post prices where the discounts are. |

## Blocklist

Terms that must not appear anywhere in the generated site. The build fails on a match. A new retailer, provider or technique is added here in the session that introduces it.

Matching ignores case, markup, spacing and punctuation, so `JB Hi-Fi` also catches `jbhifi.com.au` and a name split across a line or a tag. A term of fewer than five letters and digits is matched as written, so that `/lab` does not catch "available".

|---|---|
| Technique | `scrape`, `scraping`, `crawl`, `bot protection`, `headless`, `proxy`, `JSON-LD`, `structured data`, `affiliate`, `predictive search`, `suggest.json` |
| Retailer | `JB`, `JB Hi-Fi`, `Harvey Norman`, `Bing Lee`, `Good Guys`, `Powerland`, `Toptek`, `Betta`, `Videopro`, `Appliance Central`, `Samsung AU`, `catalogue.jbhifi`, `OzBargain`, `Press Start` |
